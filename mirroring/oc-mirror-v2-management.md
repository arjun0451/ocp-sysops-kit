# OpenShift `oc-mirror` v2 Management

This document establishes the **Standard Operating Procedure (SOP)** for managing OpenShift image mirroring via the `oc-mirror` v2 plugin.

It provides a standardized framework for:

- Environment setup
- Directory and file organization
- OpenShift release image mirroring
- Disk-to-registry synchronization
- Generated cluster resources
- Image lifecycle housekeeping
- Image deletion and registry garbage collection
- Operational validation and troubleshooting

Following this procedure helps maintain consistency, reliability, auditability, and simplified maintenance across disconnected OpenShift installations.

# 1. Overview

The `oc-mirror` v2 plugin provides a workflow for mirroring OpenShift release content into a disconnected or restricted environment.

The workflow described in this SOP uses a **two-stage mirroring process**:

```text
Quay.io / Red Hat registries
          |
          |  oc mirror --v2
          v
Local Disk / Workspace
          |
          |  oc mirror --v2
          v
Disconnected Mirror Registry
          |
          v
Disconnected OpenShift Cluster
```

The first stage downloads and stages the required content locally. The second stage transfers that content from the local workspace to the target mirror registry.

A separate deletion workflow is used to remove old release content from the mirror registry.

> **Important:** `oc-mirror` deletion removes image manifests/references. It does not necessarily reclaim the underlying registry storage. Registry garbage collection must be performed separately.

# 2. Directory Structure and Naming Conventions

Use the following directory layout consistently across mirroring hosts.

| Directory / File Path | Purpose | Naming Convention |
|---|---|---|
| `/quay-data/mirroring/configs/` | Stores `ImageSetConfiguration` and deletion configuration files | `isc-${VERSION}.yaml`, `deleteconfig-${VERSION}.yaml` |
| `/quay-data/mirroring/workspace/` | Temporary storage for mirrored archives and staging data | `workspace` |
| `/quay-data/mirroring/cache/` | Local metadata cache used to speed up mirroring | `cache` |
| `/quay-data/mirroring/logs/` | Execution logs for auditing and troubleshooting | `oc-mirror-${VERSION}.log` |
| `/quay-data/mirroring/workspace/working-dir/cluster-resources/` | Generated OpenShift manifests and configuration resources | Auto-generated by `oc-mirror` |
| `/quay-data/mirroring/oc-mirror.pid` | PID file used to prevent concurrent mirror jobs | `oc-mirror.pid` |

A recommended layout is:

```text
/quay-data/mirroring/
├── cache/
├── configs/
├── logs/
├── workspace/
└── oc-mirror.pid
```

# 5. Mirroring Workflow

The standard mirroring process consists of the following steps:

```text
1. Prepare host
       |
       v
2. Validate prerequisites
       |
       v
3. Create ImageSetConfiguration
       |
       v
4. Download mirror content to disk
       |
       v
5. Verify mirror archive/workspace
       |
       v
6. Sync content to target registry
       |
       v
7. Review generated cluster resources
       |
       v
8. Apply required resources to disconnected cluster
```

---

## 5.1 Create the ImageSetConfiguration

Create the configuration directory:

```bash
mkdir -p /quay-data/mirroring/configs
```

Create:

```text
/quay-data/mirroring/configs/isc-4.18.50.yaml
```

Example configuration:

```yaml
apiVersion: mirror.openshift.io/v2alpha1
kind: ImageSetConfiguration

mirror:
  platform:
    channels:
      - name: eus-4.18
        type: ocp
        minVersion: 4.18.50
        maxVersion: 4.18.50

    architectures:
      - amd64

    graph: true
```

### Configuration Explanation

| Parameter | Description |
|---|---|
| `apiVersion` | API version for the v2 `ImageSetConfiguration` |
| `kind` | Defines the configuration as an `ImageSetConfiguration` |
| `mirror.platform.channels` | Defines OpenShift platform release content to mirror |
| `name` | OpenShift update channel |
| `type` | Platform type, in this case `ocp` |
| `minVersion` | Minimum release version |
| `maxVersion` | Maximum release version |
| `architectures` | Target CPU architecture |
| `graph` | Includes update graph information |

The example above mirrors OpenShift `4.18.50` for `amd64`.

## 5.2 Execute the Disk Download

The first stage downloads the mirror content to the local workspace.

Example shell script:

```bash
#!/bin/bash

# =========================
# User Variables
# =========================

VERSION="4.18.50"

BASE_DIR="/quay-data/mirroring"
CONFIG_FILE="${BASE_DIR}/configs/isc-${VERSION}.yaml"
WORKSPACE="${BASE_DIR}/workspace"
CACHE_DIR="${BASE_DIR}/cache"
LOG_FILE="${BASE_DIR}/logs/oc-mirror-${VERSION}.log"
PID_FILE="${BASE_DIR}/oc-mirror.pid"


# =========================
# Create Required Directories
# =========================

mkdir -p "${BASE_DIR}"
mkdir -p "${BASE_DIR}/configs"
mkdir -p "${BASE_DIR}/workspace"
mkdir -p "${BASE_DIR}/cache"
mkdir -p "${BASE_DIR}/logs"


# =========================
# Proxy Configuration
# =========================

export HTTP_PROXY=http://192.0.2.81:8080
export HTTPS_PROXY=http://192.0.2.126:8080
export NO_PROXY=*.,<INTERNAL_DOMAIN>

export http_proxy="${HTTP_PROXY}"
export https_proxy="${HTTPS_PROXY}"
export no_proxy="${NO_PROXY}"


# =========================
# Set Correct umask
# =========================

umask 0022

echo "umask set to $(umask)"


# =========================
# Check if Already Running
# =========================

if [ -f "${PID_FILE}" ]; then

    OLD_PID=$(cat "${PID_FILE}")

    if ps -p "${OLD_PID}" > /dev/null 2>&1; then

        echo "oc-mirror already running with PID: ${OLD_PID}"
        echo "To stop it: kill ${OLD_PID}"

        exit 1

    else

        echo "Stale PID file found. Removing..."

        rm -f "${PID_FILE}"

    fi

fi


# =========================
# Start oc-mirror
# =========================

echo "Starting oc-mirror for version ${VERSION}..."
echo "Configuration: ${CONFIG_FILE}"
echo "Workspace: ${WORKSPACE}"
echo "Cache: ${CACHE_DIR}"
echo "Log file: ${LOG_FILE}"


nohup bash -c "
    oc mirror \
        -c ${CONFIG_FILE} \
        file://${WORKSPACE} \
        --cache-dir ${CACHE_DIR} \
        --v2 \
        --retry-times 60 \
        --image-timeout 60m \
        --retry-delay 5s \
        --parallel-images 1
" 2>&1 | tee -a "${LOG_FILE}" &


# =========================
# Capture PID
# =========================

NEW_PID=$!

echo "${NEW_PID}" > "${PID_FILE}"


# =========================
# Status
# =========================

echo ""
echo "oc-mirror started in background."
echo "PID: ${NEW_PID}"
echo "Log file: ${LOG_FILE}"
echo ""
echo "Monitor:"
echo "tail -f ${LOG_FILE}"
echo ""
echo "Stop:"
echo "kill ${NEW_PID}"
```

Save the script, for example:

```text
/quay-data/mirroring/mirror-4.18.50.sh
```

Make it executable:

```bash
chmod +x /quay-data/mirroring/mirror-4.18.50.sh
```

Run it:

```bash
/quay-data/mirroring/mirror-4.18.50.sh
```

### Monitor the Mirror

```bash
tail -f /quay-data/mirroring/logs/oc-mirror-4.18.50.log
```

Check the process:

```bash
ps -ef | grep '[o]c mirror'
```

Check the PID:

```bash
cat /quay-data/mirroring/oc-mirror.pid
```

## 5.3 Sync from Disk to the Mirror Registry

After the disk-based mirror operation has successfully completed, synchronize the workspace to the target registry.

Example:

```bash
oc mirror \
  -c /quay-data/mirroring/configs/isc-4.18.50.yaml \
  --from file:///quay-data/mirroring/workspace \
  docker://<MIRROR_REGISTRY>:<PORT> \
  --v2 \
  --dest-tls-verify=false
```

### Command Explanation

| Option | Purpose |
|---|---|
| `-c` | Specifies the `ImageSetConfiguration` |
| `--from` | Specifies the local mirror workspace |
| `file://` | Indicates the source is local disk |
| `docker://` | Specifies the destination registry |
| `--v2` | Uses the `oc-mirror` v2 workflow |
| `--dest-tls-verify=false` | Disables destination TLS verification |

> **Security recommendation:** Avoid `--dest-tls-verify=false` in production unless the registry is intentionally configured with an untrusted/self-signed certificate and the operational security policy permits this configuration. Prefer installing and trusting the correct CA certificate.

### Example Successful Output

A successful operation may look similar to:

```text
[INFO] : Hello, welcome to oc-mirror
[INFO] : setting up the environment for you...
[INFO] : environment version: 4.22.0-202607010254.p2.g3033291.assembly.stream.el9-3033291
[INFO] : workflow mode: diskToMirror
[INFO] : Verified we can authenticate against registry "<MIRROR_REGISTRY>:<PORT>"
[INFO] : Extracting mirror archive(s)...

[INFO] : going to discover the necessary images...
[INFO] : collecting release images...
[INFO] : Start copying the images...
[INFO] : images to copy 188
```

The image copy operation should eventually reach:

```text
188 / 188 100 %
```

The final result should indicate successful mirroring:

```text
[INFO] : === Results ===
[INFO] :  ✓ 188 / 188 release images mirrored successfully
```

## 5.4 Generated Cluster Resources

After successful mirroring, `oc-mirror` generates resources under:

```text
/quay-data/mirroring/workspace/working-dir/cluster-resources/
```

Typical files include:

```text
cluster-resources/
├── idms-oc-mirror.yaml
├── itms-oc-mirror.yaml
├── signature-configmap.json
├── signature-configmap.yaml
└── updateService.yaml
```

### IDMS

`idms-oc-mirror.yaml` contains an `ImageDigestMirrorSet`.

Its purpose is to map image digests to the disconnected mirror registry.

### ITMS

`itms-oc-mirror.yaml` contains an `ImageTagMirrorSet`.

Its purpose is to map image tags to the disconnected mirror registry.

### Signature ConfigMap

The signature configuration contains image signatures required for image verification.

Files may include:

```text
signature-configmap.json
signature-configmap.yaml
```

### UpdateService

```text
updateService.yaml
```

This configures the OpenShift Update Service (OSUS) information needed for disconnected update workflows.

### Catalog Resources

If operator catalogs are mirrored, additional resources may be generated.

If no catalogs are mirrored, `oc-mirror` may report:

```text
No catalogs mirrored. Skipping CatalogSource file generation.
No catalogs mirrored. Skipping ClusterCatalog file generation.
```

# 6. Housekeeping and Image Deletion

## 6.1 Why Housekeeping Is Required

`oc-mirror` v2 does not automatically prune old images from the registry as part of normal mirroring.

Without housekeeping, old OpenShift release content can accumulate and consume significant registry storage.

Recommended lifecycle:

```text
Mirror new release
       |
       v
Validate new release
       |
       v
Retain required releases
       |
       v
Identify obsolete releases
       |
       v
Generate deletion manifest
       |
       v
Review deletion list
       |
       v
Delete image manifests
       |
       v
Run registry garbage collection
       |
       v
Verify reclaimed storage
```

---

## 6.2 Create the DeleteImageSetConfiguration

Create a deletion configuration for the release to be removed.

Example:

```text
/quay-data/mirroring/configs/deleteconfig-4.18.46.yaml
```

Configuration:

```yaml
kind: DeleteImageSetConfiguration
apiVersion: mirror.openshift.io/v1alpha2

delete:
  platform:
    channels:
      - name: eus-4.18
        minVersion: 4.18.40
        maxVersion: 4.18.40
```

The values should be changed to match the exact release or release range approved for deletion.

> **Operational requirement:** Review the deletion configuration carefully before executing the deletion. Ensure the selected release is no longer required by any disconnected OpenShift cluster.

---

## 6.3 Generate the Deletion Manifest

Generate the list of images that would be deleted.

Example:

```bash
oc mirror delete \
  --config /quay-data/mirroring/configs/deleteconfig-4.18.46.yaml \
  --workspace file:///quay-data/mirroring/workspace \
  --v2 \
  --generate \
  docker://<MIRROR_REGISTRY>:<PORT>
```

Expected output:

```text
[INFO] : Hello, welcome to oc-mirror
[INFO] : setting up the environment for you...
[INFO] : workflow mode: delete
[INFO] : going to discover the necessary images...
[INFO] : collecting release images...
[INFO] : Generating delete file...
[INFO] : /quay-data/mirroring/workspace/working-dir/delete file created
```

The generated file is typically:

```text
/quay-data/mirroring/workspace/working-dir/delete/delete-images.yaml
```

### Review the Deletion Manifest

Before applying the deletion:

```bash
less /quay-data/mirroring/workspace/working-dir/delete/delete-images.yaml
```

Or:

```bash
cat /quay-data/mirroring/workspace/working-dir/delete/delete-images.yaml
```

Verify:

- Target registry
- Repository paths
- Release version
- Image count
- Image digests
- No required release is included

---

## 6.4 Execute Image Deletion

Once the deletion manifest has been reviewed and approved:

```bash
oc mirror delete \
  --delete-yaml-file /quay-data/mirroring/workspace/working-dir/delete/delete-images.yaml \
  docker://<MIRROR_REGISTRY>:<PORT> \
  --v2
```

Example successful result:

```text
[INFO] : === Results ===
[INFO] : ✓ 189 / 189 release images deleted successfully
```

The command may also report:

```text
Remember to execute a garbage collect (or similar) on your remote repository
```

This message is important.

# 8. Important Operational Notes

## 8.1 `umask`

Always use:

```bash
umask 0022
```

Incorrect permissions can cause generated files to be unreadable or unusable by other operational accounts/processes.

---

## 8.2 Registry Garbage Collection

`oc-mirror delete` removes the selected image manifests from the registry.

It does **not** necessarily release the physical storage immediately.

The registry must perform garbage collection to reclaim unreferenced blobs.

For Quay or another registry implementation, use the platform's documented garbage-collection procedure.

Conceptually:

```text
oc-mirror delete
       |
       v
Image manifests removed
       |
       v
Unreferenced blobs remain
       |
       v
Registry garbage collection
       |
       v
Physical disk space reclaimed
```

---

## 8.3 Do Not Delete Releases Still in Use

Before deleting an OpenShift release, verify:

- No cluster still requires the release.
- No installation or upgrade is currently using the release.
- No rollback procedure requires the release.
- Required signatures and metadata remain available.
- The release is outside the organization's retention policy.

A recommended retention policy should be defined by the platform operations team.

Example:

```text
Current release       -> Retain
Previous release      -> Retain
Rollback release      -> Retain
Obsolete release      -> Candidate for deletion
Approved deletion     -> Delete
Registry GC            -> Reclaim storage
```

---

## 8.4 Review Before Deletion

Always generate the deletion file first:

```bash
oc mirror delete ... --generate ...
```

Then review:

```bash
cat /quay-data/mirroring/workspace/working-dir/delete/delete-images.yaml
```

Only after approval should the actual deletion command be executed.

---

## 8.5 TLS Verification

The following option disables destination TLS verification:

```bash
--dest-tls-verify=false
```

Use it only when explicitly required.

For production environments, the preferred approach is to configure the correct trusted certificate authority and use normal TLS verification.

---

## 8.6 Parallelism

The example mirroring script uses:

```text
--parallel-images 1
```

This intentionally limits concurrent image operations.

Increasing parallelism may improve throughput, but it can also increase:

- CPU utilization
- Network utilization
- Registry load
- Disk I/O
- Memory consumption

Change this setting only after validating resource capacity.

---

## 8.7 Retry Configuration

The example uses:

```text
--retry-times 60
--image-timeout 60m
--retry-delay 5s
```

These settings are intended to tolerate transient network or registry failures.

Tune them according to the network reliability and operational requirements of the environment.

# 9. Troubleshooting

## 9.1 `umask` Warning

### Symptom

```text
Detected bad umask 002
```

### Resolution

```bash
umask 0022
```

Verify:

```bash
umask
```

Expected:

```text
0022
```

---

## 9.2 Existing `oc-mirror` Process

### Symptom

The mirror script reports:

```text
oc-mirror already running with PID: <PID>
```

### Resolution

Check the process:

```bash
ps -p <PID>
```

If it is a valid mirror process, allow it to continue.

If the PID is stale:

```bash
rm -f /quay-data/mirroring/oc-mirror.pid
```

Then restart the operation.

---

## 9.3 Stale PID File

The script automatically checks whether the PID in the PID file is still active.

If the process no longer exists:

```text
Stale PID file found. Removing...
```

The PID file can safely be recreated by the next mirror operation.

---

## 9.4 Insufficient Disk Space

Check:

```bash
df -h /quay-data
```

Also identify large directories:

```bash
du -sh /quay-data/mirroring/*
```

Before deleting anything, verify that the data is no longer required.

---

## 9.5 Registry Authentication Failure

Verify authentication:

```bash
podman login <MIRROR_REGISTRY>:<PORT>
```

Also verify:

- Registry DNS resolution
- Network connectivity
- Credentials
- Registry certificate trust
- Proxy and `NO_PROXY` settings
- Registry availability

---

## 9.6 Proxy Connectivity Problems

Check:

```bash
env | grep -i proxy
```

Confirm that:

```text
HTTP_PROXY
HTTPS_PROXY
NO_PROXY
http_proxy
https_proxy
no_proxy
```

are correctly configured.

Internal registry and cluster endpoints should normally be included in `NO_PROXY` where required by the environment.

- [ ] No authentication errors
